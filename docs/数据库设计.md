# 数据库设计

## 1. 集合划分

数据库名为 `survey_system`，一共用了五个集合：

| 集合 | 存放内容 |
| --- | --- |
| users | 用户账号 |
| surveys | 问卷基本信息和状态 |
| questions | 每道题目 |
| responses | 每次提交的答卷 |
| sessions | 登录 session（connect-mongo 自动维护） |

题目没有放在 `surveys` 文档里，答卷也没有放在 `surveys` 文档里。这样每个集合的职责比较清楚，问卷列表查询时不用把大量题目和答卷一起读出来。

## 2. users

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| _id | ObjectId | 用户编号 |
| username | string | 用户名，唯一 |
| password_salt | string | 随机盐 |
| password_hash | string | scrypt 计算出的密码摘要 |
| created_at | Date | 注册时间 |

示例：

```javascript
{
  _id: ObjectId("66f000000000000000000001"),
  username: "demo",
  password_salt: "8c2f...",
  password_hash: "a10b...",
  created_at: ISODate("2026-09-20T01:00:00Z")
}
```

不保存明文密码，也不在接口里返回 `password_hash` 和 `password_salt`。

## 3. surveys

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| _id | ObjectId | 问卷编号 |
| owner_id | ObjectId | 创建者，对应 users._id |
| public_id | string | 公开短编号，唯一 |
| title | string | 标题 |
| description | string | 说明 |
| allow_anonymous | boolean | 是否允许匿名填写 |
| allow_multiple | boolean | 是否允许同一人填写多次 |
| status | string | draft / published / closed |
| deadline | Date 或 null | 截止时间 |
| question_count | number | 题目数量，方便列表显示 |
| created_at | Date | 创建时间 |
| updated_at | Date | 更新时间 |
| published_at | Date 或 null | 发布时间 |
| closed_at | Date 或 null | 关闭时间 |

示例：

```javascript
{
  _id: ObjectId("66f100000000000000000001"),
  owner_id: ObjectId("66f000000000000000000001"),
  public_id: "campus26",
  title: "校园生活小调查",
  description: "想了解一下大家平时的校园生活。",
  allow_anonymous: true,
  allow_multiple: true,
  status: "published",
  deadline: ISODate("2026-11-02T02:37:00Z"),
  question_count: 6,
  created_at: ISODate("2026-10-12T02:00:00Z"),
  updated_at: ISODate("2026-10-14T08:00:00Z"),
  published_at: ISODate("2026-10-14T08:00:00Z"),
  closed_at: null
}
```

`question_count` 有一点冗余，但它只是列表显示用的计数，在添加或删除题目时同步更新，查询列表时不用再对 questions 做一次分组。

## 4. questions

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| _id | ObjectId | 题目编号 |
| survey_id | ObjectId | 所属问卷 |
| order | number | 题号，从 1 开始 |
| type | string | single / multiple / text / number |
| title | string | 题干 |
| required | boolean | 是否必答 |
| options | array | 选项数组，只有选择题有 |
| min_choices | number 或 null | 多选最少选择数 |
| max_choices | number 或 null | 多选最多选择数 |
| exact_choices | number 或 null | 多选必须选择数 |
| min_length | number 或 null | 文本最少字数 |
| max_length | number 或 null | 文本最多字数 |
| min_value | number 或 null | 数字最小值 |
| max_value | number 或 null | 数字最大值 |
| integer_only | boolean | 数字是否必须为整数 |
| jump_rules | array | 跳转规则 |

选项的结构是：

```javascript
[
  { key: "A", text: "食堂" },
  { key: "B", text: "外卖" },
  { key: "C", text: "自己做" }
]
```

用 `key` 存答案，比存选项文字稳定。即使以后修改选项文字，已经有答案的 key 也不会变。不过这一阶段发布后不允许改题，所以暂时不会出现改选项文字的情况。

跳转规则的结构是：

```javascript
[
  { condition: { option: "A", match: "any" }, target_order: 4 },
  { condition: { option: "B", match: "any" }, target_order: 2 }
]
```

数字题的规则：

```javascript
[
  { condition: { op: "gte", value: 30 }, target_order: 6 }
]
```

跳转规则放在题目文档里，因为规则本来就是“这道题回答后怎么走”的一部分，读取题目时一起取出来，不用再查一个规则集合。

## 5. responses

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| _id | ObjectId | 答卷编号 |
| survey_id | ObjectId | 所属问卷 |
| respondent_id | ObjectId 或 null | 填写人，匿名时为 null |
| respondent_name | string 或 null | 填写人用户名，匿名时为 null |
| respondent_key | string | 用户和问卷算出的 HMAC，用于限制重复填写 |
| anonymous | boolean | 是否匿名提交 |
| answers | array | 本次答卷的答案 |
| submitted_at | Date | 提交时间 |

answers 的结构：

```javascript
[
  {
    question_id: ObjectId("66f200000000000000000101"),
    question_order: 1,
    type: "single",
    value: "A"
  },
  {
    question_id: ObjectId("66f200000000000000000104"),
    question_order: 4,
    type: "number",
    value: 20
  }
]
```

多选题的 `value` 是数组，例如 `["A", "C"]`。文本题是字符串，数字题是数字。

答案数组只保存实际走到并填写的题目。跳过的题不会出现。可选的题如果没填，也不保存。

## 6. sessions

这个集合由 `connect-mongo` 自动创建，保存登录 session 和过期时间。它不算业务数据，但放在 MongoDB 里可以让服务重启后登录状态仍然保留。

## 7. 索引

| 集合 | 索引 | 作用 |
| --- | --- | --- |
| users | `{ username: 1 }` unique | 防止重复用户名，登录时快速查 |
| surveys | `{ public_id: 1 }` unique | 根据公开链接找问卷 |
| surveys | `{ owner_id: 1, created_at: -1 }` | 查某个用户的问卷列表 |
| questions | `{ survey_id: 1, order: 1 }` unique | 按问卷取题目并保证题号不重复 |
| responses | `{ survey_id: 1, submitted_at: -1 }` | 按问卷取答卷和统计 |
| responses | `{ survey_id: 1, respondent_key: 1 }` | 限制重复填写时查是否填过 |

## 8. 为什么这样设计

### 8.1 为什么不把所有内容放在一个集合

如果把题目和答卷都嵌在 survey 文档里，会有一个很长的数组。每次添加一道题都要把整个问卷文档读出来再写回去；答卷多了以后，问卷文档会越来越大，列表查询也会读到不需要的内容。分开之后，每次只操作需要的那几道题或那一份答卷。

### 8.2 为什么答卷里的 answers 又用嵌套数组

一份答卷是一个整体，提交后一般不会单独修改其中一道题。统计时按 `survey_id` 找到答卷，再展开 answers，比较方便。把 answers 单独拆成一个集合也可以，但这一阶段没必要，反而多一次关联查询。

### 8.3 为什么不用关系数据库

问卷的题目类型不同，字段也不同：选择题有选项和数量限制，文本题有长度限制，数字题有范围限制。用关系表要拆成题目表、选项表、规则表，还要处理很多可空字段。MongoDB 的文档结构可以把一道题完整地放在一个文档里，前端和后端传 JSON 也比较直接。

### 8.4 为什么适合 MongoDB

- 题目和选项的结构不固定，文档模型比较自然。
- 一次答卷的答案放在一个数组里，读取和统计方便。
- 问卷发布后题目不变，不需要复杂的事务修改。
- 统计可以直接用 `$unwind`、`$group`、`$avg` 等聚合操作完成。
- 数据量不大时，几个集合加索引已经够用。

## 9. 冗余和一致性

系统里有少量冗余：

- `surveys.question_count` 是题目数量的缓存。
- `responses.respondent_name` 是提交时的用户名快照。
- `answers.question_order` 是提交时的题号快照。

这些冗余都不会影响主要数据。`question_count` 只在加题、删题时更新；`respondent_name` 只用于显示非匿名答卷，不参与权限判断；`question_order` 用于统计时按题号排序，题目发布后不再变化，所以不会出现不一致。
